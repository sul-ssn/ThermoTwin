# ThermoTwin

Локальный MVP цифрового двойника тепловой сети по ТЗ G-TON 2026. Синтетическая модель микрорайона, GIS-схема, совместная достижимость по подаче и обратке, сценарии изоляции, резервные ветки, виртуальная телеметрия, ограниченная гидравлика и PDF.

## Запуск

```sh
docker compose up --build
```

Интерфейс Compose: http://localhost:3000. Текущий локальный запуск: http://localhost:3001 (порт 3000 занят). OpenAPI: http://localhost:8000/docs.

| Пользователь | Пароль | Роль |
|---|---|---|
| dispatcher | demo-dispatcher | Расчёты, инциденты, отчёты |
| admin | demo-admin | Также импорт и аудит |
| observer | demo-observer | Только чтение |

Это локальные демонстрационные учётные данные. Для другого окружения задайте `THERMOTWIN_USERS` JSON-объектом с полями `password` и `role` для каждого пользователя; настройте TLS на reverse proxy. Токены ограничены 8 часами и хранятся в памяти сервера.

### Без Docker

Нужны Python 3.12+, Node.js 22+ и npm. SQLite используется автоматически, если DATABASE_URL не задана.

```sh
uv venv backend/.venv --python 3.12
uv pip install --python backend/.venv/bin/python -r backend/requirements.txt
cd backend
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

В другом терминале:

```sh
cd frontend
npm ci
PORT=3001 npm run dev
```

`NEXT_PUBLIC_API_URL` задаёт адрес backend (по умолчанию http://localhost:8000). CORS_ORIGINS — разрешённые origins через запятую.

## Проверки

Из корня проекта:

```sh
cd backend
.venv/bin/python -m pytest -q
cd ../frontend
npm run typecheck
npm run build
npx playwright test
cd ..
PYTHONPATH=backend backend/.venv/bin/python scripts/benchmark.py
PYTHONPATH=backend backend/.venv/bin/python scripts/benchmark_kostanay.py
```

Результаты измерений сохраняются в docs/kpi-report.json. Скрипт фиксирует конфигурацию, размеры контрольной квадратной сети, 20 последовательных запусков и нагрузку из 10 одновременных вычислений. Эта сеть используется как нагрузочный fixture, а не как карта района. HTTP-проверка выполняется scripts/benchmark_http.py на текущей модели запущенного backend; результат — docs/kpi-http-report.json. Сохранённые замеры от 10 октября относятся к demo-2. Видео демонстрации пока не подготовлено.

Для текущей карты подготовлен [отдельный отчёт KPI и корректности kostanay-yubileyny-1](docs/kpi-kostanay.md) и [исходные измерения JSON](docs/kpi-kostanay.json). `benchmark_kostanay.py` запускает независимую проверку всех участков, backend-тесты, замеры ядра и отдельный временный API с собственной SQLite; рабочая история сценариев не изменяется. По умолчанию: 11 контрольных сценариев, по 50 последовательных измерений и 5 пачек по 10 одновременных HTTP-запросов на сценарий.

## Демонстрация

1. Войти как dispatcher. Карта: Казахстан → Костанайская область → Костанай → микрорайон «Юбилейный». Модель содержит 538 узлов, 672 трубы двух контуров и 63 здания.
2. Открыть «Симуляции», выбрать «Разрыв трубы» и участок `S-ROAD-0000`.
3. На шаге ограничений включить резервные ветки и запустить расчёт.
4. Сравнить варианты, посмотреть зону отключения и операции.
5. Выбрать вариант, зарегистрировать инцидент и скачать его PDF; проверить предпросмотр на экране «Отчёты».
6. Проверить обновления телеметрии и историю событий.
7. Войти как admin, импортировать новую версию модели и посмотреть аудит.

Интерфейс обновлён по предоставленному дизайн-концепту: [описание и проверки](docs/design-update.md).

Трассировка повторяет дороги и проезды района из OpenStreetMap, с ответвлениями к контурам зданий. Источник, арматура, диаметры и нагрузки смоделированы; это не исполнительная схема теплосети. [География, источники и воспроизведение модели](docs/kostanay-model.md).

## Архитектура и ограничения

- Next.js / TypeScript / MapLibre. Схема без внешней подложки работает без доступа к картографическому сервису.
- FastAPI, NetworkX, SciPy; отдельный пул процессов для расчётов. HTTP-запрос ожидает завершения worker.
- SQLAlchemy: SQLite локально, PostgreSQL в Compose. Снимки сети и результатов сохраняются в JSON; PostGIS доступен в Compose, но пространственные индексы пока не используются.
- Версии сети неизменяемы. PDF строится из сохранённого backend-результата и снимка модели, включает схему.
- Демо-генератор каждые 30 секунд; штатный режим / разрыв / утечка / потеря связи, журнал показаний, WebSocket и резервный HTTP polling. Внешний тестовый источник сохраняется отдельно от генератора.
- **Участковая задвижка в синтетической модели представляет полную изоляцию ребра.** Реальная геометрия арматуры с двумя концами повреждённого участка требует отдельной модели, проверенной инженером. Импорт допускает одну такую задвижку на ребро.
- Отказ задвижки означает невозможность переключения; движок ищет разрез доступной арматурой. Если источник нельзя отделить, сценарий получает `infeasible`.
- Поиск резервов жадный; глобальная оптимальность отключений не гарантируется. Сначала ранжируются кандидаты, прошедшие ограничения гидравлики, затем число отключений и операций. Для остальных явно указано, что допустимость не подтверждена.
- Гидравлика — стационарная линейная модель Δp=R·Q, R в бар/(м³/ч). Нагрузка переводится в расход при ΔT=40°C. Нет насосных кривых, теплообмена и нестационарных процессов; это не полноценный инженерный расчёт.
- Снижение давления меняет граничное давление в отдельном сценарии, не подменяет графовую отключённость: недостаточность давления отражается статусом гидравлики.
- Идентификаторы глобально уникальны. Параллельные трубы поддерживаются как отдельные рёбра с суммарной проводимостью.
- Redis/Celery, полноценные таблицы каждой предметной сущности, управление пользователями, MQTT/OPC UA, i18n для казахского и инженерная верификация ещё не реализованы. См. docs/implementation-status.md.

Синтетическая сеть явно помечена. Управления реальной инфраструктурой нет.

Браузерные тесты используют локально установленный Google Chrome через Playwright, TEST_BASE_URL по умолчанию http://localhost:3001. Для другого компьютера настройте launchOptions в frontend/playwright.config.ts. Скриншоты — docs/dashboard*.png.
